# 7. Tactics questionnaire

The table follows the tactics-based questionnaire for security in SAiP (Table 11.2). It has one row
per tactic in Chapter 11's security tactics tree, plus rows for the authentication features a
reviewer would expect to see discussed (multi-factor authentication, session timeout,
token-based authentication). "Supported" means the prototype implements the tactic. "Risk" rates
what the gap would cost if this design were deployed beyond its trusted-network assumption:
H (high), M (medium), L (low). For a supported tactic, the risk is the risk that remains.

| Tactic group | Tactic question | Supported? (Y/N) | Risk (H/M/L) | Design Decisions and Location | Rationale and Assumptions |
| --- | --- | --- | --- | --- | --- |
| Detect Attacks | **Detect Intrusion**: does the system compare request patterns with known attack signatures? | N | M | None. Failed logins and denials are recorded (Audit) but not analysed | Out of scope for a two-tactic prototype. The audit log is the raw material an intrusion detector would read |
| Detect Attacks | **Detect Service Denial**: does the system detect floods of requests? | N | M | None | No rate limiting. Each authenticated request costs a bcrypt check (about 70 ms), so a flood of requests with credentials is cheap to send and costly to serve. Acceptable on a trusted network |
| Detect Attacks | **Verify Message Integrity**: are messages protected against tampering (checksums, MACs)? | N | M | None | Integrity in transit would come from TLS, which is not used (see Encrypt Data) |
| Detect Attacks | **Detect Message Delay**: are replayed or delayed messages detected? | N | L | None | HTTP Basic requests carry no nonce or timestamp, so a captured request can be replayed. Covered by the trusted-network assumption |
| Resist Attacks | **Identify Actors**: are the sources of external input identified? | Y | L | The username in the HTTP Basic header on every request; read by `BasicAuthenticationFilter` (Section 3) | No session or token: the caller is identified again on each request. A request without the header is anonymous |
| Resist Attacks | **Authenticate Actors**: are actors' identities verified? | Y | M | HTTP Basic, `DaoAuthenticationProvider` with `DemoUserDetailsService`, `{bcrypt}` hashes checked by the delegating `PasswordEncoder` (`SecurityConfig`, `authn`) | Passwords are stored only as BCrypt hashes (cost 10). A wrong password and an unknown user give identical 401 responses and similar timing. Risk stays M because the credentials cross the network in reversible form (Encrypt Data) |
| Resist Attacks | **Multi-factor authentication**: is more than one factor required? | N | M | None | One factor (password). A second factor would not fit stateless HTTP Basic without a separate login exchange |
| Resist Attacks | **Token-based authentication** (for example OAuth 2.0 / JWT bearer tokens) | N | M | None; HTTP Basic sends the password itself on every request (decision D2) | Tokens would limit how often the password crosses the network and allow expiry, but would need a token issuer. Basic keeps the authentication path short and visible for the course |
| Resist Attacks | **Authorize Actors**: is access controlled per actor or per role? | Y | L | Per role: URL rules generated from `AccessRules` by `AccessPolicy`, with the role hierarchy from `SecurityConfig`. Per actor: `OwnRecordGuard` through `@PreAuthorize` (`access`) | The table is data, so the rules, the tests and the README come from one source. All 72 cells of the access matrix are checked (Section 9) |
| Resist Attacks | **Limit Access**: is access to resources restricted beyond what is needed? | Y | L | `anyRequest().denyAll()` as the last URL rule (`AccessPolicy`); stateless, no session; no browser client | A URL not listed in the table is denied to every user, ADMIN included. A new controller is unreachable until it is given a row |
| Resist Attacks | **Limit Exposure**: are the number of access points and the data exposed kept small? | Y | L | Nine services only; error bodies hold only status, error and path (`ApiError`); `/api/admin/users` returns no hashes; a patient gets 403 before any 404 | The 403-before-404 order means a patient cannot discover which patient ids exist |
| Resist Attacks | **Encrypt Data**: are data and credentials encrypted in transit and at rest? | N | H | None. The server listens on plain HTTP; data is held in memory unencrypted | HTTP Basic over plain HTTP sends Base64-encoded, reversible credentials on **every** request. The only mitigation is the assumption that the network is trusted (Section 2). A deployment would need TLS before anything else |
| Resist Attacks | **Separate Entities**: are sensitive parts isolated from the rest (separate processes, networks)? | N | L | None. One process, one in-memory store | Not needed for a prototype; the security logic is at least separated into its own packages and a single filter chain |
| Resist Attacks | **Validate Input**: is input checked for well-formedness and range? | Partly | M | Path ids are bound to `long` by Spring MVC, so a non-numeric id is rejected; JSON bodies are bound to typed records | No range or business validation of vitals or prescriptions. Not a focus of the two tactics |
| Resist Attacks | **Change Credential Settings**: are default credentials changed and credentials rotated? | N | M | Seeded users in `DemoUsers` with published demo passwords | The passwords are public on purpose so each user type can be tried (README). A real system would keep users outside the code and force a change on first login (p. 175) |
| React to Attacks | **Revoke Access**: can an actor's access be withdrawn while the system runs? | N | M | None. Users and roles are fixed in code | Because nothing is cached between requests, removing a user from the store would take effect on the next request; there is just no service to do it |
| React to Attacks | **Restrict Login**: are repeated failed logins limited (lockout, back-off)? | N | M | None. Failed attempts are recorded as `AUTHN_FAILURE` but not counted | Without lockout, passwords can be guessed online. bcrypt slows each guess to about 70 ms, which helps but does not stop it |
| React to Attacks | **Re-authentication / session timeout**: are idle sessions ended? | N/A | L | No sessions exist (`SessionCreationPolicy.STATELESS`) | Every request is authenticated again, so there is no session to expire. The cost is a bcrypt check per request (decision D3) |
| React to Attacks | **Inform Actors**: are operators or users told about an attack? | N | L | None. An administrator can read `GET /api/admin/audit`, but nothing is pushed | Notification would be built on the audit events |
| Recover from Attacks | **Audit**: are security-relevant actions recorded? | Y | M | `SecurityEventListener` records `AUTHN_SUCCESS`, `AUTHN_FAILURE` and `AUTHZ_DENIED` into `InMemoryAuditLog` and the application log (`audit`) | Risk M: the log is in memory, bounded to the newest 1000 entries, and lost on restart. A malformed Basic header is refused before an event is published, so it is not recorded (Section 3) |
| Recover from Attacks | **Nonrepudiation**: can an actor deny having made a request? | N | M | None | Audit entries are not signed and the password is shared knowledge in this demo, so an entry does not prove who acted |
